CHAPTER 1: INTRODUCTION TO PROCESSES

1.1 What Is a Process?

A process is a program in execution. A program stored on a disk is passive: it contains instructions and data, but it does not perform work until the operating system loads it and gives it resources. A process is the active execution environment formed from those instructions, its current processor state, memory, and operating-system-managed resources.
A process changes as it runs. Its program counter identifies the next instruction, CPU registers hold temporary values, and its stack stores function-call information. It may also own open files, communication endpoints, and other resources. The operating system tracks these details so it can pause a process, resume it, isolate it from others, and reclaim its resources when it finishes.
For example, opening a browser may create one or more processes. A browser process can render pages, handle user input, and communicate with other processes. The exact process organization depends on the browser and operating system.

A process is one of the most important abstractions supplied by an operating system. It represents an executing program together with the information required to manage that execution. The word “active” is important: a program file can exist for years without running, while a process changes state as instructions execute, wait for input, and interact with the system.

At a particular instant, a process has a current instruction address, processor register values, a stack, memory mappings, and resource references. These elements make it possible to suspend a process and later continue it as though its execution had simply paused. The kernel maintains control information and enforces boundaries between processes.

Processes are useful because applications need a controlled way to use shared hardware. Without the process abstraction, applications would need to manage the CPU, memory, and devices directly, making systems difficult to protect and coordinate. The OS creates a consistent environment in which each process can make progress while other processes exist.

Example: when a student opens a web browser, the operating system creates an execution instance. The browser may then create helper processes for page rendering, extensions, or media. The process abstraction allows the OS to schedule these activities and limit the damage if one component fails.

Practical note: a process is not necessarily equal to one application window. One application can own multiple processes, and one process can support multiple windows or tasks. The relationship depends on the application architecture.

1.2 Program, Process, and Job

A program is a set of instructions saved as a file. A process is a running instance of a program. A job is a unit of work submitted to a computer system, often used in batch-processing and scheduling contexts. One program can have several process instances, and a job may involve one or multiple processes.
Consider a word-processing application. Its executable file is the program. When two users launch it, the system may create two separate processes, each with its own address space and state. A print request submitted to a print queue can be treated as a job that waits until the printer service can handle it.
These terms are related but not interchangeable. Programs describe instructions; processes describe execution; jobs describe submitted work or a scheduling unit.

A program is a passive collection of instructions, usually stored as an executable file or script. A process is an active instance of a program. A job is a unit of work submitted for execution or managed by a scheduling system. The distinctions become especially useful when studying batch systems, operating-system services, and process creation.

One program can be started more than once. Each instance may have its own data, current instruction position, and resources. For example, two calculator instances can run the same executable but show different values because their process states are separate.

A job may be broader than a process. In a batch environment, a job can include input files, commands, dependencies, and a desired output. A scheduler may admit the job when the required resources are available. In interactive systems, the term job can also refer to a command or task managed by a shell.

These distinctions help clarify scheduling questions. The program describes what instructions are available; the process describes the execution context; and the job describes the submitted work unit or administrative task. A question about CPU scheduling usually asks which ready process or thread gets processor time.

1.3 Why Processes Are Important

Processes provide a practical structure for multiprogramming, protection, and resource management. A system can keep several programs ready and switch among them, improving CPU utilization when one program waits for input or storage. Process isolation limits accidental interference: one process normally cannot directly overwrite another process's private memory.
The operating system also uses processes to account for resources, enforce permissions, respond to failures, and provide a predictable interface to applications. If a program crashes, its process can usually be terminated without shutting down the whole computer. Process abstractions are therefore central to reliability, responsiveness, and security.

Processes support multiprogramming: while one process waits for disk, keyboard, or network activity, another can use the CPU. This overlap improves overall hardware utilization. A system that ran only one program at a time would often leave the processor idle during slow input/output operations.

Process isolation is also a security and reliability feature. Separate address spaces help prevent one process from accidentally modifying another process's private memory. The OS can enforce permissions and terminate a failed process while keeping unrelated applications alive.

Processes provide a unit for resource accounting. The operating system can track CPU time, memory, open files, and other resources, and can apply limits or policies. Administrators can inspect processes to identify resource-intensive applications or stop misbehaving workloads.

Process management is not free. Creating processes consumes kernel bookkeeping and memory resources, and communication between isolated processes requires an IPC mechanism. System designers balance isolation against overhead based on the application’s needs.

1.4 Process Address Space

A process address space is the range of virtual addresses available to that process. A typical layout contains a text or code region, initialized data, uninitialized data (often called BSS), a heap, and a stack. The code region contains instructions. Data regions hold global and static variables. The heap supports dynamically allocated objects. The stack supports function calls, local variables, and return information.
The heap often grows upward while the stack grows downward, although actual layouts vary by platform and runtime. Virtual memory allows each process to see a logical address space that can be mapped to physical memory. This mapping supports isolation, sharing of selected pages, demand paging, and relocation.

A process may also map shared libraries, memory-mapped files, and shared-memory regions. The operating system and processor memory-management unit enforce access permissions such as read, write, and execute.

A process address space is the virtual address range that a process can use. Virtual addresses are translated to physical memory by hardware and operating-system-managed page tables. This arrangement lets each process operate as if it has its own memory layout, even when physical memory is shared or pages are temporarily stored elsewhere.

The code or text segment contains executable instructions. The data segment holds initialized global and static variables, while BSS commonly represents zero-initialized or uninitialized global data. The heap is used for dynamic allocation, and the stack stores function-call frames, local variables, saved registers, and return information.

Memory layout is a conceptual model rather than a universal fixed diagram. Shared libraries, memory-mapped files, thread stacks, guard pages, and runtime-managed regions may appear in different locations. Address-space randomization may also vary region placement to make attacks harder.

Example: a program allocates a list dynamically. The list's objects may reside on the heap, while a local pointer referring to the list may be stored in the current stack frame. If the process accesses an address outside permitted mappings, the processor raises an exception that the OS handles.

1.5 Process Control Block

The process control block (PCB) is an operating-system data structure containing information needed to manage a process. Common fields include the process identifier, process state, program counter, CPU registers, scheduling priority, memory-management information, accounting data, and information about open resources.
When a process is switched out, its execution context is saved so it can later continue. The PCB, together with associated kernel structures, stores or references the information required for that continuation. The PCB is not the process itself; it is the kernel's record of the process.
A PCB can be thought of as a process dossier. The scheduler consults scheduling fields, the memory manager uses address-space information, and resource-management code tracks files and other objects. Its exact layout is operating-system-specific.

The process control block is a kernel-managed record that stores or points to information needed to manage a process. It typically includes a PID, process state, scheduling information, saved CPU context, memory-management details, accounting information, and resource references.

The PCB is especially important during a context switch. When a running execution entity is interrupted, the system preserves the values needed to resume it. The next selected entity's saved context is restored. The PCB and related kernel structures make this bookkeeping possible.

Not every operating system stores every item in one contiguous structure. Some information may be distributed among kernel objects, tables, or architecture-specific records. The PCB is best understood as a logical collection of process-management data.

Think of the PCB as a record card for the kernel. It does not contain the entire program's code or all of its memory. Instead, it records the process's identity, execution state, resource relationships, and the information needed to administer it.

1.6 Process Identifiers and Relationships

An operating system assigns a process identifier (PID) to distinguish a process. A parent process may create child processes, forming a process tree or broader relationship graph. A child may inherit selected attributes, such as environment settings or open file descriptors, depending on the operating system and creation method.
On Unix-like systems, fork() traditionally creates a child process and exec() can replace a process's program image. wait() allows a parent to collect a child's termination status. Windows uses different process-creation APIs. These are examples of interfaces, not universal rules.
Process relationships help with supervision and cleanup. A parent can launch worker processes, monitor their results, and coordinate their termination. PID values can be reused after a process exits, so a PID alone is not always a permanent identity.

2.1 The Basic Process-State Model

The basic process-state model describes a process as being in one of several states. New means the process is being created. Ready means it can run but is waiting for CPU time. Running means its instructions are currently executing on a processor. Waiting or blocked means it cannot proceed until an event occurs, such as completion of an input/output operation. Terminated means it has finished or has been stopped.

This model is intentionally simplified. Real systems may include suspended-ready, suspended-blocked, stopped, or other states. The key distinction is whether a process is eligible to execute and whether it is waiting for an external event.

2.2 State Transitions

A process moves from new to ready when the system admits it. The scheduler dispatches a ready process to running. A running process may return to ready when its time slice expires or a higher-priority process preempts it. It may enter waiting when it requests I/O or waits for a synchronization event. When that event completes, it returns to ready. A process enters terminated when execution ends or the system ends it.
State transitions are triggered by events, not simply by elapsed time. A process blocked on a disk request does not become ready merely because another process has used the CPU for a long time. It must wait for the requested event.

2.3 Process Creation

Processes may be created during system startup, when a user launches an application, when a service starts a worker, or when an existing process requests a child. Creation requires the operating system to allocate and initialize a process record, assign an identifier, establish memory mappings, set up resource references, and place the process into an appropriate state.
Creation strategies vary. Some systems create a new process image directly; others use a create-and-replace sequence. Copy-on-write can make process creation efficient by allowing parent and child to initially share physical pages while marking them so that a write causes a private copy. This avoids copying every page immediately.

2.4 Process Termination

A process may terminate normally after completing its task, or abnormally because of an error, an exception, a user request, or a system policy. The operating system closes or releases resources, records an exit status, and updates relationships with parent or supervising processes.

2.5 Context Switching

A context switch occurs when the processor stops executing one thread and begins executing another. The kernel saves the outgoing execution state—such as registers and program counter—and restores the incoming state. Scheduling decisions and bookkeeping may occur during the switch.
Context switching enables multitasking, but it is overhead: during the switch, the CPU is not advancing the user-level work of either task. Switching may also affect caches and translation lookaside buffers. The cost depends on hardware, kernel design, address-space changes, and workload. Frequent switching can reduce throughput, while too little switching can make interactive systems feel unresponsive.

3.1 What Is a Thread?

A thread is a unit of execution within a process. Each thread has its own program counter, register set, and stack, while threads in the same process generally share the process's code, global data, heap, and open resources. A process can contain one thread or many.
Threads are useful when an application has multiple activities, such as receiving user input, downloading data, and rendering a screen. If one thread waits for I/O, another can continue. On multicore hardware, independent threads may execute simultaneously, provided the program and system permit it.

3.2 Processes Compared with Threads

Processes provide stronger isolation because their address spaces are normally separate. Threads within one process share memory and can communicate efficiently through shared data, but this sharing introduces synchronization requirements. Creating and switching between threads may be less expensive than doing so between processes, though actual costs depend on implementation.
Use separate processes when fault isolation, security boundaries, or independent resource ownership are important. Use threads when tasks need shared data or low-overhead communication. Many applications combine both approaches: a browser may use multiple processes for isolation and multiple threads inside each process for concurrent work.

3.3 User-Level Threads

User-level threads are managed by a runtime library without requiring the kernel to know about each individual thread. Their creation and switching can be fast because the runtime can perform operations in user space. However, in a many-to-one design, if one thread makes a blocking system call, the kernel may block the entire process and therefore all user threads. Such threads also cannot independently run on multiple CPU cores when the kernel sees only one schedulable entity.
User-level scheduling can be tailored to application needs, but it must cooperate with the kernel and handle blocking operations carefully.

3.5 Thread Mapping Models

The many-to-one model maps many user threads to one kernel thread. It has low management overhead but cannot provide true parallel execution across cores, and a blocking call may stall all threads.
The one-to-one model maps each user thread to a kernel thread. It supports parallelism and independent blocking, but creating very large numbers of threads can consume resources.

6.4 Deadlock

Deadlock is a condition in which a set of processes or threads are permanently blocked because each is waiting for a resource or event that another member of the set must provide. The four classic necessary conditions are mutual exclusion, hold and wait, no preemption, and circular wait.
Prevention breaks at least one condition. Avoidance makes allocation decisions using information about future resource needs. Detection allows deadlocks to occur and then identifies them. Recovery may terminate processes or reclaim resources. A practical strategy is to impose a global lock ordering, reducing circular-wait risk.
Deadlock differs from starvation. In deadlock, a group is stuck due to a dependency cycle; in starvation, one task is repeatedly denied progress while other tasks continue.

6.6 Producer-Consumer Problem

In the producer-consumer problem, producers place items into a bounded buffer and consumers remove them. The buffer must not overflow or underflow. A typical semaphore solution uses a mutex for buffer access, an empty counter initialized to the buffer capacity, and a full counter initialized to zero.
A producer waits for an empty slot, locks the buffer, inserts an item, unlocks, and signals that an item is available. A consumer waits for an available item, locks the buffer, removes it, unlocks, and signals that a slot is empty. The order of operations is important to avoid deadlock and incorrect counts.

6.7 Readers-Writers and Dining Philosophers

The readers-writers problem models shared data that many readers may inspect while writers require exclusive access. Policies may favor readers, favor writers, or aim for fairness. Reader preference can starve writers; writer preference can delay readers. A fair policy seeks to prevent indefinite postponement.
The dining philosophers problem models competing tasks that each need multiple resources. If every philosopher holds one fork and waits for another, circular wait can cause deadlock. Solutions include resource ordering, allowing at most N−1 philosophers to compete simultaneously, or using a waiter to grant resource pairs safely.
