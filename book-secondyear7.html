Chapter 1: Introduction

1.1 Introduction

An operating system coordinates many programs that compete for limited resources. A process may need processor time, memory, files, printers, database records, network connections, or other devices. Resource allocation determines which process receives a resource, when it receives it, and when it must release it.

A deadlock occurs when a group of processes becomes permanently blocked because each is waiting for a resource or event that another process in the group can provide. Deadlocks are important because they can stop useful work even when a computer still has available processing power. They can appear in operating systems, databases, distributed applications, and systems that use locks or shared devices.

This guide explains the foundations of resource allocation, the four necessary conditions for deadlock, resource-allocation graphs, prevention, avoidance, detection, and recovery. It also distinguishes deadlock from starvation and livelock and applies the ideas to practical computing scenarios.

Learning outcomes

After studying this guide, learners should be able to explain how operating systems allocate resources; identify the four necessary conditions for deadlock; interpret resource-allocation graphs; compare prevention, avoidance, detection, and recovery; describe the Banker’s algorithm at a conceptual level; and recommend safer synchronization and resource-management practices.

How to use this guide

Study the lessons in sequence and redraw the diagrams in your own notes. Complete the activities before answering the assessment. For calculation and algorithm questions, show each step rather than giving only the final result.

Key idea: Deadlock management is about coordinating resource ownership and waiting so that processes can make progress safely.

Chapter 1: Introduction

1.2 Processes, Resources, and Concurrency

Learning focus: Understand the operating-system concept and recognize how it appears in practical computing.

An operating system runs processes that perform work. A process is an executing program together with its current state, memory, and allocated resources. Many processes appear to run at the same time because the operating system switches among them or executes them on multiple processor cores.

Concurrency allows several processes to make progress during overlapping periods. It improves responsiveness and resource use, but it creates coordination challenges when processes share data or hardware. A process may need a resource temporarily, use it, and then release it so another process can proceed.

CONCEPT OVERVIEW

Process A Operating system Process B Shared resources

Deadlock is one possible outcome of poor coordination. Understanding processes and resources is therefore the starting point for studying deadlocks.

Chapter 1: Introduction

1.3 Understanding Resource Allocation

Learning focus: Understand the operating-system concept and recognize how it appears in practical computing.

Resource allocation is the process of assigning system resources to processes that request them. Resources may be physical, such as printers and memory, or logical, such as files, locks, database connections, and communication channels.

An allocation request generally involves a process asking for a resource, the operating system or resource manager checking availability and policy, and the resource being granted or the process being made to wait. When the process finishes using the resource, it should release it.

CONCEPT OVERVIEW

Process requests Resource manager Grant or wait Process releases

Allocation policy affects efficiency, fairness, and safety. A policy that grants every request immediately may create conflicts, while a policy that is too restrictive can reduce performance. The system must balance progress and protection.

Chapter 1: Introduction

1.4 Resource Types and Resource Instances

Learning focus: Understand the operating-system concept and recognize how it appears in practical computing.

A resource type describes a category of resource, while an instance is one particular usable unit of that type. For example, a system may have one scanner resource type with two physical scanner instances, or a pool of database connections with several available instances.

Some resources are reusable: a printer, lock, or memory buffer can be used by one process and later assigned to another. Other resources may be consumable, such as a message or signal that is produced and then received. Deadlock analysis often focuses on reusable resources because ownership and release are central to the problem.

CONCEPT OVERVIEW

Resource type Instance A Instance B Available pool

Knowing whether a resource has one instance or multiple instances matters. A cycle in a resource-allocation graph has a stronger implication when every resource type in the cycle has only one instance.

Chapter 1: Introduction

1.5 Process States and Resource Needs

Learning focus: Understand the operating-system concept and recognize how it appears in practical computing.

A process changes state as it executes. Common states include new, ready, running, waiting or blocked, and terminated. A process can become blocked when it requests a resource that is not currently available.

Resource needs can change throughout execution. A process might acquire a file lock, read data, request a second lock, update a record, and then release both locks. If several processes acquire resources in different orders, they may form a circular dependency.

CONCEPT OVERVIEW

Ready Running Waiting Completed

Good program design makes resource needs predictable. Developers should document which resources are acquired, in what order, and where they are released, including error and exception paths.

Chapter 1: Introduction

1.6 The Resource Allocation Graph

Learning focus: Understand the operating-system concept and recognize how it appears in practical computing.

A resource-allocation graph is a directed graph used to represent processes and resource types. Process nodes are often drawn as circles, and resource nodes as rectangles. A request edge points from a process to a resource; an assignment edge points from a resource to a process.

The graph helps visualize who owns each resource and which process is waiting. A cycle indicates a potential deadlock. If each resource type has exactly one instance, a cycle is both necessary and sufficient for deadlock in the basic model. With multiple instances, a cycle alone does not prove deadlock.

CONCEPT OVERVIEW

Process requests resource Resource is assigned Another process waits Trace possible cycle

To analyze a graph, identify every request and assignment edge, trace directed paths, and check how many instances each resource type has. Never conclude that every cycle automatically means deadlock in a multi-instance system.

Chapter 1: Introduction

1.7 What Is a Deadlock?

Learning focus: Understand the operating-system concept and recognize how it appears in practical computing.

A deadlock is a situation in which a set of processes is blocked because each process is waiting for an event or resource that can be caused or released only by another process in the same set. As a result, none of the processes can continue.

A simple example involves two processes and two locks. Process A owns Lock 1 and requests Lock 2. Process B owns Lock 2 and requests Lock 1. Each process waits for the other to release its lock, but neither can reach the code that releases its current lock.

CONCEPT OVERVIEW

Process A holds Lock 1 Process A waits for Lock 2 Process B holds Lock 2 Process B waits for Lock 1

Deadlock is different from a slow system. In a deadlock, the blocked processes cannot make progress without outside intervention or a change in resource ownership.

Chapter 2: The Four Necessary Conditions

2.1 The Four Necessary Conditions

Learning focus: Understand the operating-system concept and recognize how it appears in practical computing.

Four conditions must all hold simultaneously for a deadlock to occur in the classic operating-system model: mutual exclusion, hold and wait, no preemption, and circular wait. These are known as the Coffman conditions.

Mutual exclusion means at least one resource cannot be shared. Hold and wait means a process holds one resource while requesting another. No preemption means a resource cannot simply be taken away; it must be released voluntarily. Circular wait means a chain of processes exists in which each waits for a resource held by the next.

CONCEPT OVERVIEW

Mutual exclusion Hold and wait No preemption Circular wait

If a system can reliably prevent at least one of these conditions, it can prevent deadlock under the model. The challenge is choosing a prevention strategy without making the system inefficient or impractical.

Chapter 2: The Four Necessary Conditions

2.2 Mutual Exclusion

Learning focus: Understand the operating-system concept and recognize how it appears in practical computing.

Mutual exclusion means that a resource can be used by only one process at a time. It is necessary for resources that cannot safely be shared, such as a physical printer performing one print job or a lock protecting a critical section.

Some resources can be made shareable. Read-only files, immutable data, and replicated services may allow multiple processes to access information concurrently. Converting an exclusive resource into a shareable one can remove the mutual-exclusion condition for that resource.

CONCEPT OVERVIEW

Shared requests Exclusive resource One owner Release for next user

Not every resource can be shared. A printer cannot usually print two unrelated pages in the same physical operation without a queue or spooler. Designers should identify which resources truly require exclusive access and use sharing or virtualization where appropriate.

Chapter 2: The Four Necessary Conditions

2.3 Hold and Wait

Learning focus: Understand the operating-system concept and recognize how it appears in practical computing.

Hold and wait occurs when a process keeps at least one resource while waiting to acquire another. For example, a process may hold a database lock and then request a file lock while another process holds the file lock and requests the database lock.

One prevention strategy is to require a process to request all needed resources before it begins. Another is to require it to release its current resources before requesting additional ones. These policies can prevent the hold-and-wait condition but may reduce resource utilization.

CONCEPT OVERVIEW

Acquire resource A Keep A while requesting B Wait for B Potential dependency

All-at-once allocation can be difficult when a program does not know every future resource need. Releasing and reacquiring resources can also require extra work and may cause starvation if a process repeatedly loses access.

Chapter 2: The Four Necessary Conditions

2.4 No Preemption

Learning focus: Understand the operating-system concept and recognize how it appears in practical computing.

No preemption means a resource cannot be forcibly taken from a process that owns it. Many resources must be released through a controlled operation. For example, a process using a printer or updating a file may need to finish or safely cancel its operation before the resource can be reassigned.

Preemption can prevent deadlock for some resource types. If a process requests a resource that is unavailable, the system may require it to release resources it already holds and retry later. This is practical for resources whose state can be saved and restored.

CONCEPT OVERVIEW

Process owns resource New request cannot proceed Save or roll back state Release and retry

Preemption is not safe for every resource. Taking a lock away while shared data is halfway through an update could corrupt that data. The system needs a rollback, checkpoint, or other mechanism to restore a consistent state.

Chapter 2: The Four Necessary Conditions

2.5 Circular Wait

Learning focus: Understand the operating-system concept and recognize how it appears in practical computing.

Circular wait occurs when a chain of processes exists such that each process waits for a resource held by the next process in the chain, and the final process waits for a resource held by the first.

A common prevention technique is to impose a strict ordering on resource types. Every process must request resources in increasing order. If all processes follow the same global order, a circular chain cannot form.

CONCEPT OVERVIEW

Process A waits for B Process B waits for C Process C waits for A Circular dependency

Ordering must be applied consistently. If one code path acquires Lock A before Lock B while another path acquires Lock B before Lock A, the ordering rule is broken and deadlock remains possible.

Chapter 2: The Four Necessary Conditions

2.6 How Deadlocks Develop

Learning focus: Understand the operating-system concept and recognize how it appears in practical computing.

Deadlocks often develop through a sequence of individually reasonable actions. A process acquires a resource, performs work, and requests another resource. Another process has acquired the second resource and requests the first. Each request is valid in isolation, but their combination creates a cycle.

The timing of operations can determine whether a deadlock appears. A program may work correctly during many tests and still deadlock under a different scheduling order or heavier concurrency. This makes deadlocks difficult to reproduce.

CONCEPT OVERVIEW

A acquires X B acquires Y A requests Y B requests X

Developers reduce risk by reviewing lock order, minimizing the time resources are held, avoiding calls that may block while holding locks, and testing concurrent paths under stress.

Chapter 2: The Four Necessary Conditions

2.7 Deadlock Examples in Everyday Computing

Learning focus: Understand the operating-system concept and recognize how it appears in practical computing.

Deadlock-like situations can occur in many areas. A desktop application may freeze because two threads wait on locks held by each other. A database transaction may wait for a row locked by another transaction. A print workflow may be blocked by interdependent services.

Not every frozen application is deadlocked. It may be waiting for a slow device, network timeout, user input, or a process that will eventually respond. A true deadlock requires a circular or otherwise closed waiting dependency that prevents progress.

CONCEPT OVERVIEW

Application thread Lock or service Database or device Waiting dependency

When investigating a real incident, collect logs, thread or process state, lock ownership, and wait information. A visible symptom is only the starting point; the dependency structure explains the cause.

Chapter 3: Deadlock Prevention

3.1 Deadlock Prevention

Learning focus: Understand the operating-system concept and recognize how it appears in practical computing.

Deadlock prevention designs the resource-allocation rules so that at least one of the four necessary conditions can never hold. It is a proactive strategy because the system is structured to make deadlock impossible under its assumptions.

Prevention methods include making resources shareable where possible, requiring resources to be requested together, allowing safe preemption, and imposing a global resource order. Each method has trade-offs in flexibility, throughput, and resource utilization.

CONCEPT OVERVIEW

Identify necessary conditions Choose one to prevent Enforce policy Test for progress

A prevention policy should match the system. A strict ordering rule may work well for locks in a program, while all-at-once resource allocation may be unrealistic for a general-purpose operating system.

Chapter 3: Deadlock Prevention

3.2 Breaking Mutual Exclusion

Learning focus: Understand the operating-system concept and recognize how it appears in practical computing.

Breaking mutual exclusion means changing a resource so it can be shared safely. For example, a read-only data structure can be accessed by multiple processes without requiring exclusive ownership. A print spooler allows applications to submit jobs to a queue rather than controlling the printer directly.

Sharing is not always possible. When multiple processes modify the same data, synchronization may still be required to prevent race conditions. The goal is not to remove every lock, but to avoid unnecessary exclusive resources.

CONCEPT OVERVIEW

One physical resource Queue or shared abstraction Multiple clients Controlled access

Virtualization and replication can also reduce contention. A service may provide separate logical instances or copies so processes do not compete for one physical resource, although consistency and synchronization must still be managed.

Chapter 3: Deadlock Prevention

3.3 Reducing Hold and Wait

Learning focus: Understand the operating-system concept and recognize how it appears in practical computing.

A system can prevent hold and wait by requiring processes to request all resources they need before execution, or by requiring them to release held resources before requesting new ones. Both policies prevent a process from holding one resource while waiting for another.

Requesting everything at once is simple in theory but may be wasteful. A process may reserve resources long before it uses them, reducing availability for other processes. It may also be impossible to know all resource needs in advance.

CONCEPT OVERVIEW

Declare resource needs Request as a set Grant if available Release when finished

Release-before-request can lead to repeated acquisition attempts and lost work. It may be combined with checkpoints so a process can safely pause, release resources, and resume later.

Chapter 3: Deadlock Prevention

3.4 Allowing Preemption

Learning focus: Understand the operating-system concept and recognize how it appears in practical computing.

Preemption-based prevention allows the system to reclaim selected resources when a process cannot obtain a new request. The process may be rolled back to a safe checkpoint and restarted when the needed resources become available.

This approach is suitable only when the resource state can be saved, restored, or reconstructed. CPU time can be preempted easily, while a partially completed physical print operation or an unprotected update may not be safely reversible.

CONCEPT OVERVIEW

Process requests resource Check preemption support Checkpoint or rollback Retry allocation

Good preemption policies define which resources can be reclaimed, how progress is saved, and how repeated rollbacks are limited. Without these rules, a process may lose work indefinitely.

Chapter 3: Deadlock Prevention

3.5 Preventing Circular Wait

Learning focus: Understand the operating-system concept and recognize how it appears in practical computing.

A global ordering of resource types can prevent circular wait. Assign each resource type a rank, then require every process to acquire resources in ascending rank order. A process holding a higher-ranked resource cannot request a lower-ranked one.

For example, if Lock A has rank 1 and Lock B has rank 2, every code path must acquire A before B. If a process needs only B, it may acquire B directly, but it must not later request A while holding B.

CONCEPT OVERVIEW

Rank resources Acquire low rank first Acquire higher rank next No cycle can form

Resource ordering is widely used in concurrent programming, but it requires documentation and code review. Nested locks, callbacks, and library functions can introduce hidden lock acquisitions that violate the intended order.

3.6 Deadlock Avoidance

Learning focus: Understand the operating-system concept and recognize how it appears in practical computing.

Deadlock avoidance evaluates resource requests at runtime and grants a request only if doing so leaves the system in a safe state. Unlike prevention, avoidance does not prohibit every potentially risky pattern in advance; it checks the consequences of each allocation.

A safe state is one in which there exists at least one order for all processes to finish, assuming each process may request up to its declared maximum remaining needs. An unsafe state is not necessarily deadlocked, but it cannot be guaranteed to avoid deadlock under the model.

CONCEPT OVERVIEW

Current allocation New request Safety test Grant or make wait

Avoidance requires information about maximum resource demands and current allocations. It is useful in systems where these requirements are known and manageable, but it may be impractical for general workloads with unpredictable resource needs.

Chapter 3: Deadlock Prevention

3.7 The Safe-State Concept

Learning focus: Understand the operating-system concept and recognize how it appears in practical computing.

A system is in a safe state if there is a safe sequence: an ordering of processes such that each process can obtain its remaining resources, finish, and release its allocation for the next process.

Safety is a guarantee based on declared maximum needs and available resources. It does not mean every process is currently running or that no process is waiting. It means there is a possible completion order that avoids deadlock if processes stay within their declared requirements.

CONCEPT OVERVIEW

Available resources Process can finish Release its allocation Next process can finish

An unsafe state means the system has lost that guarantee. It may continue operating without deadlock, but future requests could lead to a deadlocked condition. Avoidance algorithms reject allocations that would make the state unsafe.

Chapter 4: The Banker’s Algorithm

4.1 The Banker’s Algorithm

Learning focus: Understand the operating-system concept and recognize how it appears in practical computing.

The Banker’s algorithm is a classic deadlock-avoidance method for systems with multiple instances of resource types. It compares each process’s maximum declared demand with its current allocation and the resources still available.

The algorithm first calculates each process’s remaining need. It then searches for a process whose need can be satisfied by the currently available resources. If found, the algorithm treats that process as finished and adds its allocated resources back to the available pool. It repeats until all processes can finish or no eligible process remains.

CONCEPT OVERVIEW

Calculate remaining need Find satisfiable process Assume completion Return resources and repeat

A request is safe to grant only if the resulting state passes the safety test. The algorithm is educationally important, though real systems may use different strategies because maximum needs can be hard to predict.

Chapter 4: The Banker’s Algorithm

4.2 Resource Allocation and Request Matrices

Learning focus: Understand the operating-system concept and recognize how it appears in practical computing.

Matrix representations make resource allocation easier to analyze. The Allocation matrix records how many instances of each resource type are currently assigned to each process. The Max matrix records the maximum demand each process may make. Need is calculated as Max minus Allocation.

The Available vector records the number of free instances of each resource type. A request vector describes what one process is asking for now. These values are used by the Banker’s algorithm and related safety checks.

CONCEPT OVERVIEW

Allocation matrix Maximum demand Need = Max − Allocation Available vector

All values must use consistent units and refer to the same resource types. A negative need or an allocation larger than the declared maximum indicates invalid input or an inconsistent model.

4.3 Deadlock Detection

Learning focus: Understand the operating-system concept and recognize how it appears in practical computing.

Deadlock detection allows the system to allocate resources without preventing every risky state, then checks whether a deadlock has occurred. This may be suitable when deadlocks are rare or when prevention would impose too much overhead.

Detection can use wait-for graphs for single-instance resources or matrix-based algorithms for multiple instances. The system examines which processes can finish with current resources and which remain blocked after all possible progress has been considered.

CONCEPT OVERVIEW

Collect allocation state Analyze dependencies Identify blocked set Report deadlock

Detection frequency matters. Running checks too often consumes resources, while checking too rarely allows deadlocks to persist longer. Systems may trigger detection when performance symptoms appear, at scheduled intervals, or when resource pressure becomes high.

Chapter 4: The Banker’s Algorithm

4.4 Detection Algorithms

Learning focus: Understand the operating-system concept and recognize how it appears in practical computing.

For single-instance resource types, a wait-for graph can simplify a resource-allocation graph. Each node represents a process, and an edge from one process to another means the first is waiting for a resource held by the second. A cycle indicates deadlock.

For multiple instances, detection uses available resources, current allocations, and outstanding requests. The algorithm repeatedly finds a process whose outstanding request can be satisfied, assumes it completes, and releases its allocated resources. Processes that cannot be marked complete may be deadlocked, depending on the model’s assumptions.

CONCEPT OVERVIEW

Build wait relationships Search for cycle Check resource instances Identify deadlocked processes

Detection results must be interpreted carefully. Some systems include external events, timeouts, or resource managers not represented in the model. The graph or matrix is only as accurate as the state information collected.

4.5 Deadlock Recovery

Learning focus: Understand the operating-system concept and recognize how it appears in practical computing.

After detecting a deadlock, the system needs a recovery strategy. Common approaches include terminating one or more processes, preempting resources, rolling processes back to checkpoints, or asking an administrator to intervene.

Recovery has costs. Termination may lose unsaved work; preemption may require complex rollback; and waiting for a user may leave the system unavailable. The best strategy depends on the importance of the affected processes and the ability to restore consistent state.

CONCEPT OVERVIEW

Detect deadlock Choose recovery policy Restore safe state Verify progress

Recovery should also address the underlying cause. If the same lock-order problem remains, deadlock may recur. Logs, diagnostic information, and code changes can help prevent repeated incidents.

4.6 Process Termination Strategies

Learning focus: Understand the operating-system concept and recognize how it appears in practical computing.

One recovery method is to terminate processes involved in a deadlock. The system may terminate every process in the deadlocked set or terminate them one at a time until the cycle disappears.

Choosing a process involves considering priority, work already completed, resources held, resources still needed, restart cost, and whether the process performs critical work. A database transaction may be rolled back, while an interactive application may require user notification.

CONCEPT OVERVIEW

Identify deadlocked set Select victim process Terminate or roll back Recheck dependencies

Repeatedly selecting the same low-priority process can cause starvation. Recovery policies should account for previous termination or rollback history so one process is not always sacrificed.

4.7 Resource Preemption and Rollback

Learning focus: Understand the operating-system concept and recognize how it appears in practical computing.

Resource preemption recovers a resource from a process and assigns it elsewhere. To do this safely, the system may need to save a checkpoint, undo partial work, or restart the affected process later.

Victim selection can consider the cost of preemption, the number of resources held, process priority, progress already made, and the number of times a process has been rolled back. A fair policy should avoid repeatedly selecting the same victim.

CONCEPT OVERVIEW

Select preemptible resource Save consistent checkpoint Reassign resource Resume or restart process

Some resources cannot be preempted safely. If a process is writing to a device or updating shared data, taking the resource away mid-operation can leave the system inconsistent. Recovery design must respect the resource’s semantics.

Chapter 5: Starvation and Fairness

5.1 Starvation and Fairness

Learning focus: Understand the operating-system concept and recognize how it appears in practical computing.

Starvation occurs when a process waits indefinitely because resources or CPU time are repeatedly given to other processes. Unlike deadlock, the system may continue making progress overall, but one process is continually denied its turn.

Priority scheduling, unfair locks, and repeated victim selection can contribute to starvation. Aging gradually increases the priority of a process that has waited for a long time. Fair queues and bounded waiting rules can also improve fairness.

CONCEPT OVERVIEW

Process waits Other requests repeatedly win Waiting time grows Fairness policy intervenes

A resource-management policy should consider both system throughput and individual progress. A system that completes many tasks but leaves one task waiting forever is not fair or dependable.

Chapter 5: Starvation and Fairness

5.2 Livelock and Related Problems

Learning focus: Understand the operating-system concept and recognize how it appears in practical computing.

Livelock occurs when processes remain active and repeatedly change their state in response to one another, but useful progress does not occur. For example, two systems may repeatedly yield to each other and then retry at the same time.

Deadlocked processes are typically blocked and inactive, while livelocked processes continue executing. Starvation describes one process being denied progress while others may complete. These problems require different diagnostic approaches.

CONCEPT OVERVIEW

Process A retries Process B retries Both change state No useful completion

Randomized backoff, priority rules, and carefully designed retry limits can reduce livelock. A system should distinguish useful work from repeated activity that produces no completed result.

Chapter 5: Starvation and Fairness

5.3 Deadlocks in Databases

Learning focus: Understand the operating-system concept and recognize how it appears in practical computing.

Database deadlocks occur when transactions hold locks on records, rows, tables, or other objects while requesting locks held by other transactions. For example, Transaction A updates Row 1 then requests Row 2, while Transaction B updates Row 2 then requests Row 1.

Database systems commonly detect lock cycles and choose a transaction as a victim. The victim is rolled back, releasing its locks so the other transaction can proceed. Applications should be prepared to retry transactions that are selected as victims.

CONCEPT OVERVIEW

Transaction A locks Row 1 Transaction B locks Row 2 Each requests the other row Database detects cycle

Consistent access order, short transactions, appropriate indexes, and avoiding unnecessary user interaction inside a transaction can reduce deadlock frequency. Applications should handle retryable deadlock errors safely.

Chapter 5: Starvation and Fairness

5.4 Deadlocks in Distributed Systems

Learning focus: Understand the operating-system concept and recognize how it appears in practical computing.

Distributed systems coordinate processes and resources across multiple computers. A process may wait for a remote service, message, lock, or network response. Because state is spread across machines, detecting a global cycle is more difficult than in one operating system.

Network delay and failures can make waiting look like deadlock. A remote process may be slow, disconnected, or crashed. Distributed deadlock detection therefore needs careful treatment of timeouts, stale information, message ordering, and failure detection.

CONCEPT OVERVIEW

Service A waits on B Service B waits on C Service C waits on A Global dependency cycle

Leases, timeouts, distributed lock services, idempotent operations, and clear ownership rules can reduce risk. A timeout alone does not prove deadlock; it is a policy decision that a wait has lasted too long.

Chapter 5: Starvation and Fairness

5.5 Synchronization Tools and Locks

Learning focus: Understand the operating-system concept and recognize how it appears in practical computing.

Synchronization tools coordinate concurrent access to shared data. A mutex allows one thread at a time to enter a protected region. Semaphores control access to a limited number of identical resources. Read-write locks allow multiple readers or one writer under defined rules.

These tools prevent race conditions when used correctly, but they can also create deadlocks if locks are acquired in inconsistent orders or held too long. Condition variables and events allow threads to wait for a condition without continuously checking it.

CONCEPT OVERVIEW

Thread requests lock Synchronization primitive Critical section Release and notify

Good synchronization practice includes documenting lock ownership, keeping critical sections short, using a consistent acquisition order, avoiding blocking operations while holding locks, and releasing resources on every exit path.

5.6 Practical Design and Troubleshooting

Learning focus: Understand the operating-system concept and recognize how it appears in practical computing.

Preventing deadlocks in real systems requires design discipline and observation. Developers should map resource dependencies, define a lock order, avoid nested locks where possible, and keep resource ownership limited to the work that requires it.

When a system hangs, collect process or thread states, lock ownership, stack traces, database wait information, and logs. Look for cycles and determine whether the waiting processes depend on one another or are waiting on an external event.

CONCEPT OVERVIEW

Observe blocked processes Map resource ownership Find dependency cycle Apply and verify fix

After resolving the incident, reproduce the issue if possible, add tests for the problematic interleaving, and improve monitoring. A fix should address the dependency pattern rather than merely increasing timeouts.

Chapter 6: Developing Practical Understanding

6.1 Developing Practical Understanding

Use these approaches to connect the theory to software and systems you encounter.

Observe lock behavior

Study a simple multithreaded program that uses two locks. Trace the order in which each thread acquires and releases the locks. Discuss how reversing the order could create a circular wait.

Explore a database transaction

Use a training database or a classroom demonstration to observe how transactions update records. Learn how the database reports a deadlock and why an application may need to retry a transaction.

Practice resource graphs

Draw a graph with process nodes and resource nodes. Add request and assignment edges one at a time. Determine whether a cycle exists and whether the number of resource instances changes the conclusion.

Review safe-state calculations

Practice small Banker’s algorithm examples. Calculate each process’s remaining need, find a process whose need can be met, and return its allocation to the available pool as though it completed.

Reflect

Which strategy seems most practical for the system you studied: prevention, avoidance, detection, or recovery? Explain what information the system has and what trade-offs matter.
