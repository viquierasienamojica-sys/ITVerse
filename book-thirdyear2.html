Chapter 1 — Introduction to Web Technologies

Chapter overview

This chapter explains the foundational ideas behind introduction to web technologies and connects

them to practical web development. Each section includes an explanation, a realistic example, and

implementation considerations for beginning IT students.

1.1 Understanding the Internet and the Web

The Internet is the interconnected network infrastructure that carries data among devices. The World

Wide Web is a collection of linked resources accessed through browsers using web protocols. A

website is typically hosted on a server and identified by a domain name. The distinction matters:

email and other Internet services can operate without a web browser.

Design consideration

A website should remain understandable when connections are slow.

Developers can compress images, use meaningful error messages, and test the application on

different devices.

Key idea

Understanding the Internet and the Web is best understood as part of a complete

request-to-response workflow, rather than as an isolated definition.

1.2 How Websites Work

A browser takes a URL, resolves its hostname, connects to a server, requests resources, and

interprets the returned HTML, CSS, and JavaScript. A webpage may require many requests for

fonts, images, scripts, and data. Servers can respond with stored files or generate responses

dynamically.

Technical note

Distinguish a protocol from a product: HTTP defines message semantics, while a

particular browser, server, or framework implements those semantics in software.

Key idea

How Websites Work is best understood as part of a complete request-to-response

workflow, rather than as an isolated definition.

1.3 Client-Server Architecture

A client initiates requests, while a server listens and responds. This separation makes it possible for

many devices to use the same application. A web server may forward requests to an application

process, which reads data from a database and constructs the response.

1.4 Static and Dynamic Websites

A static page is delivered largely as stored content. A dynamic application can vary its response

according to the requested URL, authenticated user, or stored data. Modern sites often combine

static assets, browser-side rendering, and server-generated responses.

2.1 What a Browser Does

A browser is a software application that retrieves, interprets, and displays web resources. Examples

include Chrome, Firefox, Safari, and Edge. Browsers manage tabs, navigation, downloads,

permissions, and privacy settings while enforcing security boundaries between sites.

2.2 Browser Components

The user interface includes the address bar, back and forward controls, and tabs. The networking

subsystem manages connections and resource fetching. The rendering engine builds the visual

page, while a JavaScript engine executes scripts. Storage systems maintain cookies, caches, and

site data.

2.3 Rendering HTML and CSS

After receiving HTML, the browser parses it into a Document Object Model (DOM). It parses CSS

into style rules, computes layout, paints visual elements, and composites layers. JavaScript may

change the DOM or styles, causing additional rendering work. A large script or image can delay

visible content.

send with matching requests. Cookies may support sessions, preferences, and analytics, but require

3.1 Web Server Basics

A web server accepts HTTP requests and returns HTTP responses. It may serve HTML, CSS,

JavaScript, and images directly, or act as a reverse proxy for an application. Apache HTTP Server

and Nginx are widely used examples.

3.2 Request Handling

When a request arrives, the server identifies the host and route, applies configured rules, and

chooses a response. It can return a file, redirect the client, reject unauthorized access, or pass the

request to application code. Logs help operators diagnose errors and performance issues.

3.3 Web Server vs Application Server

A web server specializes in handling HTTP traffic, static files, connection management, and

proxying. An application server runs business logic, authenticates users, and interacts with

databases. In practice, their roles can overlap, and modern frameworks can handle HTTP directly.

Chapter 4 — Hypertext Transfer Protocol (HTTP)

Chapter overview

This chapter explains the foundational ideas behind hypertext transfer protocol (http) and connects

them to practical web development. Each section includes an explanation, a realistic example, and

implementation considerations for beginning IT students.

4.1 What HTTP Is

HTTP is an application-layer request-response protocol used to transfer web resources and API

messages. It is stateless: each request has its own meaning, while applications can maintain

continuity through cookies, tokens, or other state mechanisms.

Practical example

Consider an e-library that shows book covers and a Read button. The browser

renders the interface, while a server or static hosting platform supplies the HTML and image files. If

accounts are added, authorization should be verified by a trusted backend.

What HTTP Is is best understood as part of a complete request-to-response workflow,

rather than as an isolated definition.

4.2 Request Structure

An HTTP request includes a method, target, protocol version, headers, and optionally a body. A

GET request generally retrieves a representation. POST commonly submits data for processing.

PUT is typically used to replace a resource, PATCH to modify part of it, and DELETE to request

removal.

Design consideration

A website should remain understandable when connections are slow.

Developers can compress images, use meaningful error messages, and test the application on

different devices.

Key idea

rather than as an isolated definition.

4.3 Response Structure

A response contains a status code, headers, and usually a body. The Content-Type header tells the

client how to interpret the representation. Cache-Control provides caching instructions. Location may

identify a redirect destination.

4.4 Status Codes

Codes in the 2xx range indicate success, 3xx indicate redirection, 4xx indicate client-related errors,

Modified, 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, and 500 Internal

4.5 HTTP Versions

HTTP/1.1 commonly uses persistent connections. HTTP/2 introduces multiplexed streams over a

connection and compressed headers. HTTP/3 uses QUIC over UDP to improve connection behavior

under some network conditions. The application-level semantics remain broadly consistent.

Chapter 5 — HTTPS and Secure Web Communication

Chapter overview

This chapter explains the foundational ideas behind https and secure web communication and

connects them to practical web development. Each section includes an explanation, a realistic

example, and implementation considerations for beginning IT students.

5.1 HTTP Versus HTTPS

HTTPS is HTTP carried over a secure transport, normally TLS. It protects information against

passive eavesdropping and helps detect tampering in transit. Plain HTTP does not provide these

transport protections.

A website should remain understandable when connections are slow.

HTTP Versus HTTPS is best understood as part of a complete request-to-response

5.2 TLS and Certificates

During a TLS connection, the client and server negotiate security parameters and establish keys.

The server typically presents a certificate binding its identity to a public key. The browser checks

certificate validity and whether the hostname matches. A certificate alone does not prove a website

is trustworthy in every respect.

Technical note

Distinguish a protocol from a product: HTTP defines message semantics, while a

particular browser, server, or framework implements those semantics in software.

Key idea

TLS and Certificates is best understood as part of a complete request-to-response

workflow, rather than as an isolated definition.

5.3 Confidentiality and Integrity

Encryption prevents observers from easily reading transmitted content. Integrity protection helps

detect unauthorized modifications. Authentication helps the browser establish that it is

communicating with the intended server, assuming the certificate trust system is working correctly.

HTTPS does not prevent phishing, malicious content on a legitimate site, insecure passwords, or

compromised endpoints. Secure browsing combines transport security with careful site design and

Chapter 6 — How Browsers and Servers Communicate

Chapter overview

This chapter explains the foundational ideas behind how browsers and servers communicate and

connects them to practical web development. Each section includes an explanation, a realistic

example, and implementation considerations for beginning IT students.

6.1 URL Anatomy

A URL can contain a scheme, hostname, port, path, query, and fragment. For example,

https://example.org/articles?id=7 uses HTTPS, the host example.org, the path /articles, and the

query id=7. The fragment, when present, is normally handled by the browser and is not sent as part

of the HTTP request target.

6.2 DNS Resolution

The Domain Name System translates names into records, including IP addresses. A browser or

operating system may consult caches before contacting a DNS resolver. DNS answers help locate

the destination, but DNS itself does not deliver the webpage.

6.3 Connecting and Requesting

After resolving the destination, the browser establishes a suitable network connection and

negotiates TLS for HTTPS. It then sends an HTTP request. The server processes the request and

returns headers and content. Additional resources may trigger further requests.

An Application Programming Interface (API) lets software exchange structured information. Web

APIs often use HTTP and JSON. A browser might request /api/books to retrieve a list of books and

and uniform interfaces. HTTP methods and status codes help express operations. A practical API

should use consistent URLs, clear error messages, and documented behavior.

7.3 Content Delivery Networks

A Content Delivery Network (CDN) distributes cached content across multiple locations to reduce

latency and load on an origin server. Images, scripts, and stylesheets are common CDN assets.

Cache invalidation must be planned when content changes.
