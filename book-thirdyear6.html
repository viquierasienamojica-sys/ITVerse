Chapter 1: Understanding Web Forms

1.1 Purpose and Structure of Forms

A web form collects structured information from a visitor. Registration, search, contact, checkout, and feedback interfaces all use forms.

The form element groups controls and determines how their values are submitted.

Key Concepts and Implementation

The action attribute names the destination that receives submitted data. The method attribute specifies how the browser sends it.

GET normally encodes fields in the URL query string and suits searches. POST sends data in the request body and suits creating records.

Important:

Neither GET nor POST alone provides confidentiality. HTTPS protects data while it is being transmitted.

Code Example

<form action="/search" method="get">
  <label for="q">Search lessons</label>
  <input id="q" name="q" type="search">
  <button type="submit">Search</button>
</form>

Understanding the Example

The browser uses HTML to construct form controls. CSS changes their appearance, while JavaScript can add behavior.

Practical Observation

Open the page and submit a search. Observe the query parameter in the address bar. Remove the name attribute and compare what the browser sends.

Implementation Reminder

Forms need clear labels, understandable feedback, and predictable keyboard behavior. Client-side validation cannot replace server-side validation.

Chapter 1: Understanding Web Forms Lesson 1.1

1.2 Labels, Names, and IDs

A label tells users what information a control requests. Its for attribute should match the control's id.

This allows the label to focus the field when clicked.

Key Concepts and Implementation

The name attribute identifies the submitted key, while id uniquely identifies the element in the document.

A placeholder is only a hint and should not replace a visible label. Screen readers benefit from proper label associations.

Use fieldset and legend to group related controls when needed.

Code Example

<label for="student">Student name</label>

<input
  id="student"
  name="student_name"
  autocomplete="name"
  required
>

Understanding the Example

The label is connected to the input through the matching for and id values.

The name attribute determines the field name included when the form is submitted.

Practical Observation

Click the label and check whether the input receives focus. Change the name but not the id to compare their purposes.

Implementation Reminder

Use visible labels and clear instructions so users understand each field.

Chapter 1: Understanding Web Forms Lesson 1.2

1.3 Text Inputs and Textareas

Single-line text controls work well for short responses such as usernames and subject lines.

A textarea is designed for longer, multi-line content.

Key Concepts and Implementation

The input type controls the browser interface, while the name attribute determines how the value is submitted.

Use maxlength for practical length limits, but verify length again on the server.

A disabled control is not submitted, while a readonly control is generally submitted.

Code Example

<label for="subject">Subject</label>

<input
  id="subject"
  name="subject"
  maxlength="80"
>

<label for="message">Message</label>

<textarea
  id="message"
  name="message"
  rows="5"
  required
></textarea>

Understanding the Example

The subject input accepts one line of text and limits the length to 80 characters.

The message textarea supports multiple lines and requires a value.

Practical Observation

Enter a multi-line message. Compare how the Enter key behaves in the text field and textarea.

Implementation Reminder

Provide instructions before inputs when the expected format is unfamiliar.

Chapter 1: Understanding Web Forms Lesson 1.3

1.4 Selections and Buttons

Checkboxes allow independent choices, while radio buttons represent mutually exclusive choices when they share a name.

A select element offers a menu of options. Buttons should clearly state what they do.

Key Concepts and Implementation

Checkboxes that are not selected are normally absent from submitted data.

Radio groups require a shared name and distinct values. Use fieldset and legend to explain a group of choices.

Code Example

<fieldset>
  <legend>Preferred format</legend>

  <label>
    <input
      type="radio"
      name="format"
      value="pdf"
      required
    >
    PDF
  </label>

  <label>
    <input
      type="radio"
      name="format"
      value="html"
    >
    HTML
  </label>
</fieldset>

<button type="submit">
  Save preference
</button>

Understanding the Example

Both radio buttons use the same name, so only one option can be selected at a time.

The submit button sends the selected preference when the form is submitted.

Practical Observation

Try selecting both radio options. Notice that only one remains selected. Replace radio with checkbox to compare the behavior.

Implementation Reminder

Use an explicit button type to avoid accidental form submission.

Chapter 1: Understanding Web Forms Lesson 1.4

1.5 How Submission Works

When a form is submitted, the browser identifies successful controls, applies built-in constraint checks unless disabled, and constructs a request.

The server receives the data, validates it, performs the requested operation, and sends a response.

Key Concepts and Implementation

Client-side validation does not make submitted values automatically safe.

Attackers can bypass browser checks. Production systems require server-side validation, authorization, appropriate encoding, and secure storage.

Code Example

<form action="/register" method="post">

  <label for="email">Email</label>

  <input
    id="email"
    name="email"
    type="email"
    required
  >

  <button type="submit">
    Register
  </button>

</form>

Understanding the Example

The form sends information using POST to the /register endpoint.

The email input uses built-in format validation and requires a value before normal submission.

Practical Observation

Use the browser developer tools Network panel on a test endpoint to observe requests.

Do not submit real personal data to unknown endpoints.

Implementation Reminder

Always use HTTPS when collecting real information. Client-side checks improve the user experience but cannot replace server-side security.

Chapter 2: HTML Input Types

2.1 Email, URL, Search, and Telephone

Input types provide browsers with hints about expected data and can activate built-in validation.

Email checks basic address syntax, URL checks URL syntax, search is useful for search boxes, and telephone inputs generally do not enforce a telephone number format.

Key Concepts and Implementation

Choosing the correct input type improves mobile keyboards and assistive technology behavior.

Format validation does not prove that an email inbox exists or that a URL is safe.

Telephone formats vary by region, so developers should provide clear instructions instead of assuming one universal format.

Code Example

<input type="email"
       name="email"
       required>

<input type="url"
       name="portfolio">

<input type="search"
       name="query">

<input type="tel"
       name="phone"
       autocomplete="tel">

Understanding the Example

The email input checks whether the entered value follows basic email address syntax.

The URL input expects a valid URL format. Search is intended for search queries, while telephone provides a suitable input interface for phone numbers.

Practical Observation

Test an email without an @ symbol and a malformed URL. Compare the browser feedback with the telephone input, which has no built-in format requirement.

Implementation Reminder

Always provide clear labels and instructions. Browser validation cannot replace server-side checks.

2.2 Numbers, Ranges, and Dates

The number input type accepts numeric values and supports minimum, maximum, and step constraints.

Range provides a slider for approximate numeric selection. Date, time, month, and week input types offer date-related controls when supported by the browser.

Key Concepts and Implementation

A number field is not ideal for identifiers such as postal codes or student numbers because leading zeros may be important.

Identifiers are not used for arithmetic, so a text input with an appropriate inputmode is often a better choice.

Date controls may appear differently depending on the browser, device, and locale.

Code Example

<label for="units">
  Units (1-6)
</label>

<input
  id="units"
  type="number"
  name="units"
  min="1"
  max="6"
  step="1"
>

<label for="start">
  Start date
</label>

<input
  id="start"
  type="date"
  name="start"
>

Understanding the Example

The units input accepts numbers between 1 and 6, with increments of one.

The date input allows users to select a date using the browser's supported date control.

Practical Observation

Try entering a number outside the allowed range. Observe the validation message and test how the date picker behaves on your device.

Implementation Reminder

Use the correct input type for the information being collected and verify submitted values on the server.

Chapter 2: HTML Input Types Lesson 2.2

2.3 Passwords and Autocomplete

A password input hides characters visually while the user types.

However, masking a password does not encrypt it. Secure transmission requires HTTPS.

Key Concepts and Implementation

Autocomplete tokens help browsers fill known fields such as names, email addresses, current passwords, and new passwords.

Developers should avoid unnecessarily restrictive password rules.

Longer passwords and support for password managers are recommended.

Password storage and verification must be implemented securely on the server.

Code Example

<label for="password">
  Password
</label>

<input
  id="password"
  type="password"
  name="password"
  minlength="12"
  autocomplete="new-password"
  required
>

Understanding the Example

The password input masks typed characters. The minlength attribute requires at least 12 characters during normal browser validation.

The new-password autocomplete token tells the browser that the field is intended for creating a password.

Practical Observation

Compare current-password and new-password autocomplete values. Check that the browser does not openly display typed characters.

Implementation Reminder

Use HTTPS and secure server-side password handling. Do not reveal whether an account exists through public error messages.

Chapter 2: HTML Input Types Lesson 2.3

2.4 Files, Colors, and Hidden Fields

A file input allows visitors to select files from their devices.

A color input opens a color chooser, while hidden inputs transmit values without displaying visible controls.

Key Concepts and Implementation

The accept attribute suggests which file types users may select, but it is not a security control.

File extensions and MIME types supplied by the client cannot be trusted.

The server should independently check uploaded file content, file size, permissions, and storage location.

Hidden input values can also be modified, so they must not be treated as proof of identity or authorization.

Code Example

<form
  method="post"
  enctype="multipart/form-data"
>

  <label for="attachment">
    Attach a file
  </label>

  <input
    id="attachment"
    type="file"
    name="attachment"
    accept=".pdf,.png"
  >

  <input
    type="hidden"
    name="form_version"
    value="2"
  >

</form>

Understanding the Example

The form uses multipart/form-data to support file uploads.

The file input suggests PDF and PNG files. The hidden field submits a form version value.

Practical Observation

Try choosing a file and inspect the selected filename.

Explain why the server must inspect uploaded files independently.

Implementation Reminder

File selection restrictions in HTML are not enough to protect a system. Always validate uploads on the server.

Chapter 2: HTML Input Types Lesson 2.4

2.5 Choosing the Right Input Type

Choosing an input control should begin with the nature of the data and the task the user needs to complete.

Key Concepts and Implementation

Use email inputs for email addresses, date inputs for dates, number inputs for quantities, and text inputs for identifiers.

Use radio buttons when users must select one choice, checkboxes when multiple choices are allowed, and select menus for compact option lists.

A form can be technically valid but still difficult to use.

Clear labels, helpful descriptions, keyboard access, and sensible defaults improve the user experience.

Code Example

<label for="student-id">
  Student ID
</label>

<input
  id="student-id"
  name="student_id"
  type="text"
  inputmode="numeric"
  pattern="[0-9]{8}"
  required
>

Understanding the Example

The student ID uses a text input instead of a number input because student identifiers may contain leading zeros.

The inputmode attribute suggests a numeric keyboard on supported mobile devices.

The pattern requires exactly eight digits.

Practical Observation

Try entering a student ID beginning with zero.

Observe that a text input preserves the leading zero, unlike treating the identifier as a numeric quantity.

Implementation Reminder

Choose controls based on user needs. Test forms on desktop and mobile browsers, and always validate submitted data on the server.

Chapter 3: Built-In HTML Validation

3.1 Required Fields and Basic Constraints

The required attribute prevents normal form submission when a supported control has no acceptable value.

Email and URL input types also check basic syntax. Browser constraint validation provides immediate feedback before a request is sent.

Key Concepts and Implementation

Built-in checks improve usability, but users can disable or bypass them.

Every required field must also be checked on the server.

Explain why a field is needed when its purpose is not obvious.

Code Example

<label for="contact">
  Contact email
</label>

<input
  id="contact"
  type="email"
  name="contact"
  required
>

<button type="submit">
  Continue
</button>

Understanding the Example

The email input requires the user to enter a value before normal submission.

The browser also checks whether the entered value follows basic email address syntax.

Practical Observation

Submit the form with the field empty, then with an invalid email address, and finally with a syntactically valid email address.

Compare the browser validation messages.

Implementation Reminder

Client-side validation improves the user experience but cannot replace server-side validation. Use HTTPS when collecting real information.

3.2 Minimum and Maximum Length

The minlength and maxlength attributes constrain the number of characters in supported text controls.

Minimum length is useful when a response must contain enough detail, while maximum length helps keep short fields manageable.

Key Concepts and Implementation

Length is not the same as content quality. A ten-character string may still be meaningless.

Avoid using arbitrary short password limits, and validate actual stored lengths on the server.

Code Example

<label for="summary">
  Project summary
</label>

<textarea
  id="summary"
  name="summary"
  minlength="30"
  maxlength="500"
  required
></textarea>

Understanding the Example

The textarea requires a project summary containing at least 30 characters and no more than 500 characters.

The required attribute prevents normal submission when the field is empty.

Practical Observation

Enter a short summary and attempt to submit the form.

Then enter enough text to meet the minimum length requirement. Observe when validation occurs after user input.

Implementation Reminder

Character limits should match the actual purpose of the field. Always verify input length on the server.

Chapter 3: Built-In HTML Validation Lesson 3.2

3.3 Patterns and Regular Expressions

The pattern attribute checks a text-like value against a regular expression.

It is useful for narrowly defined formats such as a fixed-length campus code.

Key Concepts and Implementation

A pattern should match the entire expected value and should be accompanied by human-readable instructions.

Avoid using complicated regular expressions to decide whether all real-world names or email addresses are valid.

Overly strict patterns can accidentally reject legitimate users.

A pattern does not make submitted information trustworthy to the server.

Code Example

<label for="code">
  Course code (ABC-123)
</label>

<input
  id="code"
  name="course_code"
  pattern="[A-Z]{3}-[0-9]{3}"
  title="Three uppercase letters, a hyphen, and three digits"
  required
>

Understanding the Example

The pattern requires three uppercase letters, followed by a hyphen and three digits.

For example, ABC-123 follows the required format.

Practical Observation

Test the following values:

  • ABC-123
  • abc-123
  • AB-123

Identify which value satisfies the pattern and explain why.

Implementation Reminder

Keep validation patterns simple and provide clear instructions about the required format.

Chapter 3: Built-In HTML Validation Lesson 3.3

3.4 Numeric Limits and Step

The min, max, and step attributes describe acceptable values for numeric and date-related controls.

A value outside the allowed range can cause a rangeUnderflow or rangeOverflow validity state.

A value that does not fit the step can cause stepMismatch.

Key Concepts and Implementation

The step attribute is not simply a visual increment for spinner buttons. It also affects validation.

Choose units carefully. For example, a price may use step="0.01", while a count usually uses step="1".

Code Example

<label for="rating">
  Rating (1-5)
</label>

<input
  id="rating"
  type="number"
  name="rating"
  min="1"
  max="5"
  step="1"
  required
>

Understanding the Example

The input accepts ratings from 1 to 5 in whole-number steps.

Values outside this range or values that do not follow the step rule can fail browser validation.

Practical Observation

Try entering these values:

  • 0
  • 3.5
  • 4

Identify whether each value violates the minimum, maximum, or step constraint.

Implementation Reminder

Use appropriate numeric limits and verify submitted values on the server.

Chapter 3: Built-In HTML Validation Lesson 3.4

3.5 Validity States and Browser Feedback

Browsers provide validity states that describe whether an input satisfies its constraints.

Common Validity States

  • valueMissing — a required value is missing.
  • typeMismatch — the value does not match the input type.
  • patternMismatch — the value does not match the required pattern.
  • tooShort — the entered value is too short.
  • tooLong — the entered value is too long.
  • rangeUnderflow — the value is below the minimum.
  • rangeOverflow — the value is above the maximum.
  • stepMismatch — the value does not follow the required step.
  • customError — a custom validation error exists.

Key Concepts and Implementation

A field is valid only when none of its applicable constraints fail.

Native error messages can differ depending on the browser and language.

Validation should clearly explain what the user needs to correct, rather than simply displaying a red border.

Code Example

const field = document.querySelector("#email");

console.log(field.validity.valueMissing);

console.log(field.validity.typeMismatch);

console.log(field.checkValidity());

Understanding the Example

The JavaScript code selects an email input and checks its validity properties.

The checkValidity() method returns true when the input satisfies its applicable constraints and false when it does not.

Practical Observation

Open the browser developer tools and inspect the validity properties after entering an invalid value.

Identify which validity state is responsible for the failure.

Implementation Reminder

Provide helpful validation messages. Client-side checks improve usability, but server-side validation remains necessary for security.

Chapter 4: Styling and Accessible Feedback

4.1 Valid and Invalid CSS States

CSS provides the :valid and :invalid pseudo-classes to style form fields based on their current validation status.

These styles help users identify whether their entered values meet the required rules.

Key Concepts and Implementation

A required empty field may match the :invalid pseudo-class before the user interacts with it.

To avoid overwhelming users, combine validation styling with careful timing and clear instructional text.

Visual appearance alone should not communicate an error.

Always keep visible focus indicators so keyboard users can identify the currently selected field.

Code Example

input:focus-visible {
    outline: 3px solid #2563eb;
}

input:invalid {
    border-color: #b91c1c;
}

input:valid {
    border-color: #15803d;
}

Understanding the Example

The focus-visible selector adds an outline when the input receives keyboard focus.

The invalid selector changes the border color when the input fails validation.

The valid selector changes the border color when the input satisfies its applicable constraints.

Practical Observation

Test keyboard navigation and check whether focused controls remain visible.

Make sure validation feedback can be understood without relying only on colors.

Implementation Reminder

Use clear error messages together with visual feedback. Never remove visible keyboard focus indicators.

4.2 Helpful Error Messages

A useful error message identifies the problem and explains how the user can correct it.

For example, "Invalid input" is less helpful than "Enter a course code like ABC-123."

Key Concepts and Implementation

Place guidance near the relevant input field and avoid clearing the user's work after a failed submission.

When possible, preserve entered values and move focus to the first invalid field.

An error summary can help users understand problems in longer forms.

Error messages should be short, understandable, and should not expose sensitive server details.

Code Example

<label for="campus">
  Campus code
</label>

<input
  id="campus"
  name="campus"
  aria-describedby="campus-help"
  required
>

<p id="campus-help">
  Use your assigned code.
</p>

Understanding the Example

The input has a visible label identifying the requested information.

The aria-describedby attribute connects the input to additional instructions.

This helps assistive technologies communicate the instructions to the user.

Practical Observation

Write a helpful error message for a missing student ID.

Compare it with a vague error message and decide which one is easier to understand.

Implementation Reminder

Explain what went wrong and how to fix it. Keep messages close to the affected field.

4.3 Labels, Instructions, and ARIA

Native HTML labels and fieldsets provide a reliable starting point for creating accessible forms.

The aria-describedby attribute connects an input to additional instructions or an error message.

The aria-invalid attribute can indicate an error state when custom validation is applied.

Key Concepts and Implementation

ARIA supports native HTML semantics, but it does not replace proper HTML structure.

Important instructions should remain visible in the interface instead of being hidden from sighted users.

Error messages must be accessible to keyboard and screen reader users.

<label for="pin">

</label>

<p id="pin-help">
  Enter six digits.
</p>

<input
  id="pin"
  name="pin"

Understanding the Example

The label identifies the input as an access code field.

The pattern attribute expects exactly six digits.

The aria-describedby attribute connects the input to the instruction "Enter six digits."

Implementation Reminder

Use native HTML labels first. Add ARIA attributes when additional accessibility information is needed.

4.4 Designing for Mobile and Keyboard

A responsive form uses readable text, sufficient spacing, clear focus indicators, and controls large enough to activate comfortably.

The inputmode attribute suggests a suitable mobile keyboard without changing the underlying input type.

Key Concepts and Implementation

Do not rely on hover effects for important instructions.

Keep keyboard tab order consistent with the visual reading order.

Avoid preventing users from pasting into password fields because they may use password managers.

Test forms using both desktop and mobile devices.

<label for="phone">

</label>

<input

  type="tel"
  name="phone"

  }

Understanding the Example

The telephone input helps browsers provide a suitable keyboard for entering phone numbers.

The autocomplete attribute allows supported browsers to suggest saved telephone information.

The CSS provides spacing inside the input and prevents it from exceeding the available width.

  • Tab
  • Shift + Tab
  • Space
  • Enter

Implementation Reminder

Design forms that work for mouse, keyboard, touch, and assistive technology users.

4.5 Avoiding Common Validation Mistakes

Common validation mistakes include using placeholders instead of labels, relying only on red borders, and requesting unnecessary information.

Other mistakes include overly strict validation patterns and rejecting submissions without explaining the problem.

Key Concepts and Implementation

A strong form reduces unnecessary steps while protecting user data.

Ask only for information needed to complete the task.

Keep forms short, provide examples where necessary, and make error messages specific.

Always validate information on the server, even when browser validation appears complete.

Code Example

<!-- Clear labels are better than
     placeholders alone -->

  Full name
</label>

<input
  id="fullname"
  name="fullname"
  autocomplete="name"
  required
>

Understanding the Example

The visible label clearly tells users what information is needed.

The autocomplete attribute allows supported browsers to suggest the user's saved name.

The required attribute prevents normal submission when the field is empty.

Practical Observation

Review a registration form you have used before.

Identify one design choice that made the form easier or harder to complete.

Implementation Reminder

Use clear labels, helpful instructions, simple validation rules, and server-side checks to create reliable forms.

Chapter 5: JavaScript Form Validation

5.1 The Constraint Validation API

JavaScript can inspect browser validity using checkValidity(), reportValidity(), and the validity property.

The checkValidity() method returns a Boolean value, while reportValidity() also asks the browser to display validation feedback.

These methods are useful when creating custom form submission processes.

Key Concepts and Implementation

Developers should not replace native browser validation without a good reason.

Built-in HTML controls are usually more consistent and accessible than completely custom implementations.

Always test empty fields, invalid values, and boundary values.

Code Example

const form = document.querySelector("form");

form.addEventListener("submit", event => {

    if (!form.checkValidity()) {

        event.preventDefault();

        form.reportValidity();

    }

});

Understanding the Example

The JavaScript selects a form and listens for its submit event.

When the form is invalid, preventDefault() stops the submission process.

The reportValidity() method asks the browser to display validation feedback to the user.

Practical Observation

Create a form with a required email field. Submit it while empty and then with a valid email address.

Observe when the submission handler blocks the request.

Implementation Reminder

Use native HTML validation when possible. Client-side checks cannot replace server-side validation and security.

Chapter 5: JavaScript Form Validation Lesson 5.1

5.2 Custom Validity Messages

The setCustomValidity(message) method allows JavaScript to mark an input as invalid using a custom explanation.

Calling setCustomValidity("") clears the custom error.

Forgetting to clear the message can cause a corrected field to remain invalid.

Key Concepts and Implementation

Custom validation is useful for rules that built-in HTML attributes cannot express clearly.

One example is checking whether two password fields contain matching values.

Custom messages should be specific and should not expose sensitive information.

Validation should run again whenever a relevant input changes.

Code Example

const confirm = document.querySelector("#confirm");

const password = document.querySelector("#password");

function match() {

    confirm.setCustomValidity(

        confirm.value === password.value
            ? ""
            : "Passwords do not match"

    );

}

confirm.addEventListener("input", match);

password.addEventListener("input", match);

Understanding the Example

The code selects the password and confirmation fields.

The match() function compares their values.

If the values match, the custom validation message is cleared.

If they are different, the confirmation field receives the message "Passwords do not match."

Practical Observation

Enter different passwords in the two fields, then make them match.

Verify that the custom error disappears when both values become equal.

Implementation Reminder

Always clear custom errors when the user corrects the input. Revalidate when related fields change.

Chapter 5: JavaScript Form Validation Lesson 5.2

5.3 Validating on Input and Blur

The input event fires while users edit the value of a form control.

The blur event occurs when focus leaves a control.

Immediate feedback can help with simple validation rules, while delayed feedback may be less distracting for longer entries.

Key Concepts and Implementation

Avoid displaying harsh error messages before users have enough time to finish typing.

A useful approach is to display instructions first and reveal errors after a field has been visited or after submission.

Accessibility requires feedback that users can understand without relying only on color.

Code Example

const email = document.querySelector("#email");

email.addEventListener("blur", () => {

    if (!email.checkValidity()) {

        email.setAttribute(
            "aria-invalid",
            "true"
        );

    } else {

        email.removeAttribute("aria-invalid");

    }

});

Understanding the Example

The JavaScript listens for the blur event on an email input.

When the user leaves the field, the code checks whether the entered value is valid.

If invalid, the aria-invalid attribute is set to true.

If valid, the attribute is removed.

Practical Observation

Type an incomplete email address, leave the field, and return to correct it.

Observe how the validation state changes after the correction.

Implementation Reminder

Display validation feedback at an appropriate time. Avoid interrupting users while they are typing.

Chapter 5: JavaScript Form Validation Lesson 5.3

5.4 Preventing Submission and Showing Errors

A submit event listener can call preventDefault() to stop a request while the application displays validation errors.

In a real application, the handler must also manage successful submission, server responses, and unexpected failures.

Key Concepts and Implementation

An application should not display "Saved successfully" until the server confirms that the operation was completed.

A form that only blocks submission without explaining the problem is difficult to use.

Developers should consider keyboard focus management and accessible error announcements.

Code Example

form.addEventListener("submit", event => {

    if (!form.checkValidity()) {

        event.preventDefault();

        form.reportValidity();

    }

});

Understanding the Example

The submit event listener checks the validity of the form.

If the form contains invalid values, preventDefault() stops submission.

The reportValidity() method requests browser validation feedback.

Practical Observation

Test the form using both valid and invalid information.

Explain why preventing a submission is different from successfully saving information.

Implementation Reminder

Do not claim that data was saved until the server confirms it. Provide clear error messages when submission fails.

5.5 Client and Server Validation

Client-side validation provides quick feedback to users.

However, server-side validation is the main security boundary.

A request can be created and sent without using the browser's form controls at all.

Key Concepts and Implementation

The server must enforce required formats, length restrictions, authorization rules, and application-specific requirements.

For example, a registration form may check email syntax in the browser.

The server must also check whether registration is allowed and whether the email address is already in use.

Parameterized database queries and appropriate output encoding help reduce injection risks.

Code Example

// Illustrative server-side pseudocode

if (!isValidEmail(request.email)) {

    return error(400, "Invalid email");

}

if (!userMayRegister(request.user)) {

    return error(403, "Not allowed");

}

createAccountSafely(request);

Understanding the Example

The first condition checks whether the submitted email address follows the required format.

The second condition checks whether the user is allowed to register.

Only after these checks does the example proceed to create the account safely.

Practical Observation

List three rules that a server must check even when the browser has already validated the form.

Implementation Reminder

Never rely only on browser validation. Use HTTPS, server-side validation, secure database operations, and proper authorization.

6.1 Student Registration Form

A student registration form collects information needed to create or update a student record.

Common fields include the student's name, email address, course, year level, and other required registration details.

Key Concepts and Implementation

Registration forms should use meaningful labels, appropriate input types, and clear instructions.

Required fields should be identified, and validation messages should explain how users can correct invalid information.

The form should collect only the information necessary for the registration process.

Code Example

<form action="/register" method="post">

  <label for="student-name">
    Full Name
  </label>

  <input
    id="student-name"
    type="text"
    name="student_name"
    autocomplete="name"
    required
  >

  <label for="student-email">
    Email Address
  </label>

  <input
    id="student-email"
    type="email"
    name="email"
    autocomplete="email"
    required
  >

  <label for="course">
    Course
  </label>

  <select
    id="course"
    name="course"
    required
  >
    <option value="">
      Select Course
    </option>

    <option value="BSIT">
      BS Information Technology
    </option>

    <option value="BSCS">
      BS Computer Science
    </option>
  </select>

  <button type="submit">
    Register
  </button>

</form>

Understanding the Example

The form uses text, email, and select controls to collect registration information.

The required attributes prevent normal submission when important fields are empty.

The email input also checks basic email address syntax.

Practical Observation

Create the registration form and test it with empty fields, invalid email addresses, and complete information.

Observe how the browser responds to different values.

Implementation Reminder

A real registration system requires a working server endpoint, secure storage, and server-side validation. HTML alone does not save student records.

6.2 Contact and Feedback Form

Contact and feedback forms allow visitors to send questions, suggestions, and comments.

These forms commonly include a name, email address, subject, and message field.

Key Concepts and Implementation

A contact form should be simple and easy to complete.

The message field should use a textarea because users may need to enter multiple lines.

Helpful instructions and reasonable character limits can improve the quality of submitted feedback.

Code Example

<form action="/feedback" method="post">

  <label for="feedback-name">
    Name
  </label>

  <input
    id="feedback-name"
    name="name"
    required
  >

  <label for="feedback-email">
    Email
  </label>

  <input
    id="feedback-email"
    type="email"
    name="email"
    required
  >

  <label for="feedback-message">
    Your Message
  </label>

  <textarea
    id="feedback-message"
    name="message"
    rows="5"
    minlength="10"
    maxlength="1000"
    required
  ></textarea>

  <button type="submit">
    Send Feedback
  </button>

</form>

Understanding the Example

The form collects the visitor's name, email address, and message.

The textarea allows a message containing multiple lines.

The minlength and maxlength attributes define acceptable character lengths.

Practical Observation

Test the form using a short message, an empty message, and a complete message.

Compare the browser validation feedback for each attempt.

Implementation Reminder

A production contact form needs a server or form service to receive messages. Protect the service against spam and malicious submissions.

6.3 Login and Password Reset Forms

Login forms allow registered users to access their accounts.

A typical login form asks for an email address or username and a password.

Password reset forms help users recover access when they forget their credentials.

Key Concepts and Implementation

Login forms should use the correct autocomplete attributes and should support password managers.

Password fields should use type="password" to mask typed characters.

A secure system must verify credentials on the server and protect authentication requests with HTTPS.

Password reset requests should avoid revealing whether a particular account exists.

Code Example

<form action="/login" method="post">

  <label for="login-email">
    Email Address
  </label>

  <input
    id="login-email"
    type="email"
    name="email"
    autocomplete="username"
    required
  >

  <label for="login-password">
    Password
  </label>

  <input
    id="login-password"
    type="password"
    name="password"
    autocomplete="current-password"
    required
  >

  <button type="submit">
    Log In
  </button>

</form>

Understanding the Example

The email field identifies the user's account.

The password input masks the characters entered by the user.

The autocomplete attributes help supported browsers and password managers recognize the login fields.

Practical Observation

Test the form with empty fields and invalid email addresses.

Explain why HTML validation cannot determine whether the user's password is correct.

Implementation Reminder

Authentication requires secure server-side processing. Never store passwords in plain text or rely on HTML validation to protect accounts.

6.4 Multi-Step Forms and Progress

Multi-step forms divide a long process into smaller sections.

This approach can make complicated registration or application forms easier to understand.

Each step should have a clear title and indicate the user's current progress.

Key Concepts and Implementation

A multi-step form should preserve information when users move backward or forward.

Users should be able to review and correct their information before final submission.

Validation can occur at each step, but all information must still be validated on the server.

Code Example

<form id="application">

  <div id="step1">

    <h2>Step 1: Personal Details</h2>

    <label for="app-name">
      Full Name
    </label>

    <input
      id="app-name"
      name="name"
      required
    >

    <button type="button" id="next">
      Next
    </button>

  </div>

  <div id="step2" hidden>

    <h2>Step 2: Review</h2>

    <p>
      Review your information.
    </p>

    <button type="button" id="back">
      Back
    </button>

    <button type="submit">
      Submit
    </button>

  </div>

</form>

<script>
const step1 = document.querySelector("#step1");
const step2 = document.querySelector("#step2");
const nameInput = document.querySelector("#app-name");

document.querySelector("#next")
  .addEventListener("click", () => {
    if (!nameInput.reportValidity()) return;
    step1.hidden = true;
    step2.hidden = false;
  });

document.querySelector("#back")
  .addEventListener("click", () => {
    step2.hidden = true;
    step1.hidden = false;
  });
</script>

Understanding the Example

The first section collects the user's name.

JavaScript checks the required field before allowing the user to continue.

The second section provides a review stage and a button to return to the previous step.

This simplified example demonstrates step navigation. A complete application would also display the entered information for review and process the final submission.

Practical Observation

Test the Next and Back buttons. Confirm that the name remains entered when returning to the first step.

Implementation Reminder

Multi-step forms should preserve entered information, show progress clearly, and validate all submitted data on the server.

6.5 Complete Validation Checklist

A validation checklist helps developers review whether a form is understandable, accessible, and secure.

The checklist should cover input types, labels, required fields, error messages, keyboard support, and server-side validation.

Key Concepts and Implementation

Validation is not complete simply because a form prevents empty submissions.

Developers must also consider incorrect formats, unexpected values, accessibility, privacy, and security.

Form Validation Checklist

  • Every input has a clear and meaningful label.
  • Required fields are identified.
  • Appropriate input types are used.
  • Minimum and maximum values are reasonable.
  • Validation messages explain how to correct errors.
  • Keyboard navigation works correctly.
  • The form is usable on mobile devices.
  • Entered information is preserved after validation errors.
  • Sensitive information is protected using HTTPS.
  • The server validates all submitted information.

Code Example

<form action="/submit" method="post">

  <label for="final-email">
    Email Address
  </label>

  <input
    id="final-email"
    type="email"
    name="email"
    autocomplete="email"
    required
  >

  <label for="final-message">
    Message
  </label>

  <textarea
    id="final-message"
    name="message"
    minlength="10"
    required
  ></textarea>

  <button type="submit">
    Submit Form
  </button>

</form>

Understanding the Example

The form uses clear labels, appropriate input types, and built-in validation attributes.

The email field checks basic email syntax, while the message field requires a minimum length.

These browser checks help users correct mistakes before submission.

Practical Observation

Review the example using the validation checklist.

Identify which requirements are handled by HTML and which still require server-side implementation.

Final Reminder

Good form validation combines clear design, accessible feedback, appropriate HTML controls, JavaScript when necessary, and secure server-side processing.
